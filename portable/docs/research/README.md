# 研究资料（research）

这三份文档是**实测记录**，不是教程。它们是 `docs/PITFALLS.md` 与
`ROADMAP.md` 里多处结论的**依据** —— 引用它们是为了让"为什么这么判"
可追溯，而不是只留一个结论。

> **为什么从 `scratch/` 搬到这里**
>
> 原来放在仓库根的 `scratch/`。那个目录同时装了两类东西：
> ① 这三份有长期价值的研究记录（22 KB）
> ② 180 个一次性诊断程序与二进制（5.4 MB，其中 88 个 exe/dll）
>
> 后者是调试过程的残留，不该进版本库。搬到这里后 `scratch/` 已删除。

## `TCC-BASELINE.md` —— TCC 能力基线矩阵

用**正确方法**（不加任何 `-I`、链接必带 `-L`）逐项实测 TCC 0.9.27
自己提供了什么、缺什么。是判断"这个垫片该不该存在"的**权威依据**。

引用它的地方：
- `AGENTS.md` 开头的"两种失败"说明
- `README.md` 的编译+链接判据
- `ROADMAP.md` 的"剩余垫片的正确范围"
- `docs/PITFALLS.md` P1 / P2 等
- `include/tccmath.h` 的边界说明

## `TOOL-AUDIT.md` —— `tool/` 目录审计与四类划分

把垫片按"该不该存在"分成四类：

| 类别 | 含义 | 处理 |
|---|---|---|
| A | TCC 已提供，垫片白做 | 删除 |
| B | TCC 缺但真头文件有 | 改用 `winapi-full` 的头 |
| C | TCC 缺且真头也没有（Vista/7 时代 API） | **保留垫片** |
| D | TCC 自身缺陷（如 float 数学） | **保留 `tccmath.h`** |

引用它的地方：`ROADMAP.md`。

## `NEXT-shim-cleanup.md` —— 垫片清理的判据

`tccwin.h` 各块的取舍理由与验证方式。
**结论是保留**：现有垫片无 bug，删除收益为零、风险非零
（曾误删 `toolchain/tcc/include/_mingw.h` 导致环境编译不了）。

引用它的地方：`docs/PITFALLS.md` P63 附近。

## 未验证边界

- 这三份文档记录的是**写入时**的实测结果，之后 TCC 头文件集有变动
  （例如整批纳入 `winapi-full-for-0.9.27`），个别条目可能已过期。
  **以 `docs/PITFALLS.md` 的编号条目为准**，那里会标注更正。
- 矩阵只覆盖当时测过的项，不是 TCC 能力的完整枚举。

## `SHIM-NECESSITY-AUDIT.md` —— `tccwin.h` 每块垫片是否必要

用项目铁律（不加项目 `-I`、链接必带 `-L`、编译+链接都过、两位宽都测）
逐块实测：**18 块里 14 块确认为必要**。

另外 4 块探测"通过"但复核后**保留** —— 文档里详细写了为什么，
其中一个原因是**我自己的探测器瞄错了对象**（用处理器拓扑去测一块
提供处理器组 API 的垫片）。这条方法论教训值得一读。

这是 `ROADMAP.md` 里"重写 tccwin.h，只保留类别 C"这条的实际判据。
